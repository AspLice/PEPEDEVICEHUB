# 第1章 プロジェクト概要

## 1.1 開発目的

複数メーカーのPC周辺機器を一元管理できる、軽量なWindows向けデスクトップアプリケーションを開発する。

メーカー純正管理ソフトウェアへの依存を可能な限りなくし、USB HID等を利用してデバイスと直接通信することを目的とする。

メーカー純正ソフトウェアを複数常駐させる必要をなくし、メモリ使用量およびCPU使用率を削減する。

## 1.2 コンセプト

- 軽量
- 高速
- モダンなUI
- 複数メーカー対応
- 高い拡張性
- オフライン動作
- 安全なハードウェア制御
- システムトレイによるバッテリー管理
- GitHubによる適切な開発管理

## 1.3 初期対応デバイス

### マウス

- メーカー：Logicool / Logitech
- 製品名：G PRO X SUPERLIGHT
- 想定世代：初代
- 接続方式：LIGHTSPEED / USB有線
- 通信プロトコル：HID++ 2.0
- 純正管理ソフト：G HUB

### キーボード

- メーカー：Akko
- 製品名：TAC75 HE
- 接続方式：USB有線
- スイッチ：磁気スイッチ
- 純正管理ソフト：Akko Cloud Driver V4 / Web Driver等

実機のVID/PID、製品名、ファームウェア、ハードウェアリビジョンを調査し、正確な対応機種を確定すること。

初代SUPERLIGHTとSUPERLIGHT 2を混同しないこと。

## 1.4 将来的な対応機器

- 他メーカーのマウス
- 他メーカーのキーボード
- ワイヤレスヘッドセット
- ワイヤレスイヤホン
- マイク
- USBレシーバー
- RGBライティング機器
- その他のPC周辺機器

特定メーカーや特定製品に依存したアーキテクチャにせず、新しいデバイスを容易に追加できる構造とする。

# 第2章 開発基本方針

## 2.1 必須方針

- Windows 11を対象とする。
- Rustをメイン言語として採用する。
- Electronを使用しない。
- メモリ使用量およびCPU使用率を極力抑える。
- インターネット接続なしで利用できる設計とする。
- メーカー純正管理ソフトの常駐を原則不要とする。
- 通常利用時に管理者権限を要求しない。
- デバイスごとの通信処理を独立させる。
- GitHubによるソースコード管理を必須とする。
- 機能単位でブランチを分ける。
- Pull Requestを経由して機能を統合する。
- 自動テストおよび実機テストを実施する。
- ハードウェアの安全性を最優先とする。

## 2.2 Codexの担当範囲

Codexは以下の作業を主体的に実施すること。

- 技術調査
- 要件整理
- アーキテクチャ設計
- GitHubリポジトリ管理
- Issue作成
- ブランチ作成
- 通信プロトコル調査
- ソースコード実装
- テストコード作成
- 自動テスト実行
- コミット
- Push
- Pull Request作成
- コードレビュー対応
- ドキュメント作成
- パフォーマンス測定
- インストーラー作成

ただし、実機への初回書き込み、正式リリース等については、後述する承認ルールに従うこと。

# 第4章 アプリケーションアーキテクチャ

## 4.1 プロセス構成

常駐処理とGUIを分離した2プロセス構成を推奨する。

### device-hub-agent.exe

常駐プロセスとして動作する。

担当機能：

- デバイス検出
- HID通信
- デバイス接続管理
- バッテリー監視
- システムトレイ表示
- バッテリー通知
- 設定保存
- GUIとのプロセス間通信
- プロファイル適用
- デバイス再接続処理

GUIを閉じた状態でも動作を継続する。

### device-hub-ui.exe

ユーザーが設定画面を開いたときに起動する。

担当機能：

- デバイス管理画面
- マウス設定
- キーボード設定
- バッテリーダッシュボード
- プロファイル編集
- トレイ設定
- アプリケーション設定
- ログおよび診断情報表示

GUIを閉じた場合は、原則としてUIプロセスを終了する。

## 4.2 プロセス間通信

Windows Named Pipe等を利用する。

- HID通信の所有権はAgentに集約する。
- GUIからデバイスへ直接通信しない。
- IPCにバージョン管理を導入する。
- 入力値の検証を行う。
- 不正なリクエストを拒否する。
- 通信タイムアウトを実装する。
- IPCは現在のユーザーからのみ利用可能とする。
- Agentの重複起動を防止する。
- GUI起動時に必要に応じてAgentを起動する。

## 4.3 デバイスアダプター

メーカーや製品固有の通信処理をアダプターとして分離する。

共通インターフェースには以下を含める。

- デバイス識別
- 接続状態取得
- 対応機能取得
- バッテリー情報取得
- 設定読み込み
- 設定書き込み
- イベント通知
- エラー処理
- 再接続処理

対応機能はCapabilityとして管理する。

UIはCapabilityに基づいて動的に構成し、対応していない機能や未検証の機能を操作可能にしないこと。

## 4.4 設計上の注意

- 通信処理とGUI描画を分離する。
- 長時間の通信処理でGUIを停止させない。
- 同一デバイスに対する通信を適切に直列化する。
- デバイスの切断や通信失敗を前提とした設計とする。
- Mock Deviceによる実機不要の開発環境を用意する。

# 第6章 通信プロトコル調査および解析

## 6.1 既存情報の調査

対象デバイスについて以下を調査する。

- メーカー公式SDK
- 公開API
- 公開通信仕様
- GitHub上の既存実装
- WebHIDを利用した公式ドライバー
- オープンソースのデバイス管理ソフト

参考プロジェクト：

- https://github.com/libusb/hidapi
- https://github.com/libratbag/libratbag
- https://github.com/pwr-Solaar/Solaar
- https://github.com/openrazer/openrazer

- https://github.com/PyFlat/Device-Battery-Info

既存実装については、対応機種、動作環境、コードの正確性、ライセンスを確認すること。

## 6.2 通信解析手順

既存情報だけで実装できない場合は、ユーザー所有のデバイスを対象に通信解析を行う。

1. USBデバイスおよびHIDインターフェースの特定
2. HID Report Descriptorの調査
3. 純正ソフトウェア起動時の通信取得
4. 現在の設定読み込み時の通信取得
5. 設定変更前後の通信取得
6. 変更項目と通信内容の比較
7. Report IDとデータ長の特定
8. 各バイトの意味の特定
9. エンディアンの調査
10. チェックサムの調査
11. 応答データの調査
12. エラー処理の調査
13. 通信仕様書の作成
14. 検証済みプロトコルのRust実装

通信解析にはWireshark、USBPcap等を使用する。

設定変更は原則として一度に1項目のみ行い、通信内容の差分を特定すること。

## 6.3 通信仕様書

解析結果を以下の情報とともに記録する。

- 対象製品
- ハードウェアリビジョン
- VID/PID
- ファームウェアバージョン
- 接続方式
- 対応インターフェース
- コマンド一覧
- パケット構造
- Report ID
- データ長
- 設定値の範囲
- 応答形式
- エラーコード
- 実機検証結果
- 未確認事項
- 参考資料
- ライセンス

未確認の通信仕様を確定情報として扱わないこと。

## 6.4 通信データの安全管理

- 必要なデバイスの通信のみ取得する。
- 不要なキーボード入力を取得・保存しない。
- 認証情報や個人情報を含む通信をGitHubに登録しない。
- 生の通信キャプチャは原則ローカル環境で管理する。
- テストデータには匿名化済みのパケットのみ使用する。

# 第7章 Logicool G PRO X SUPERLIGHT対応

## 7.1 基本方針

G PRO X SUPERLIGHTを最初の実機対応デバイスとする。

バッテリー監視を最優先で実装し、その後設定変更機能を追加する。

初代SUPERLIGHTを想定するが、実機検出結果から正確な世代を確定すること。

## 7.2 参考実装

特に以下を重点的に調査する。

- https://github.com/Lken-cmd/SuperLightBattery
- https://github.com/pwr-Solaar/Solaar
- https://github.com/libratbag/libratbag

SuperLightBatteryについては、Windows上でのバッテリー残量取得、イベント通知、システムトレイ表示の参考とする。

## 7.3 デバイス識別

参考となる識別情報：

- Vendor ID：0x046D
- デバイス識別候補：0x4093、0xC094
- 通信方式：HID++ 2.0

上記は既存実装を調査する際の候補であり、実機照合を必須とする。

USBレシーバーのPIDと、その配下の論理デバイス識別情報を区別すること。

## 7.4 HID++通信基盤

- HID++ 2.0通信を実装する。
- 対応Featureを動的に検出する。
- Feature Indexを固定値として扱わない。
- デバイスインデックスを適切に判定する。
- リクエストとレスポンスを正しく対応付ける。
- 非同期通知と通常応答を分離する。
- 有線接続とLIGHTSPEED接続の両方に対応する。
- 通信タイムアウトを実装する。
- 通信失敗時の無制限リトライを禁止する。

## 7.5 バッテリー関連

以下のFeatureを優先的に調査する。

| Feature ID | 機能 |
|---|---|
| 0x1004 | Unified Battery |
| 0x1000 | Battery Status |

実機が公開するFeatureに基づき、正しい取得方式を選択する。

実装対象：

- バッテリー残量
- 充電状態
- 低残量状態
- 接続状態
- スリープ状態
- 最終取得時刻
- システムトレイ表示
- バッテリー低下通知

## 7.6 設定関連

以下のFeatureを調査する。

| Feature ID | 機能 |
|---|---|
| 0x2201 | Adjustable DPI |
| 0x8060 | Report Rate |
| 0x8100 | Onboard Profiles |
| 0x1B04 | Reprogrammable Controls |

Feature IDの存在のみを理由に、機能が利用可能と判断してはならない。

## 7.7 実装対象機能

優先度：最優先

- バッテリー残量取得
- 充電状態取得
- トレイアイコン表示

優先度：高

- DPI取得・変更
- DPIステージ管理
- ポーリングレート取得・変更
- オンボードプロファイル管理

優先度：中

- ボタン割り当て
- スリープ設定（対応する場合）

優先度：低

- ファームウェア情報表示
- その他の対応設定

LOD、デバウンスタイム、アングルスナップ等は、実機が対応している場合のみ追加する。

ファームウェア更新機能は初期開発対象外とする。

# 第8章 Akko TAC75 HE対応

## 8.1 基本方針

Akko TAC75 HEについては、磁気スイッチ関連の設定機能を重点的に実装する。

純正ドライバーの通信仕様が公開されていない場合は、Webドライバーまたはデスクトップドライバーの通信を解析する。

## 8.2 参考資料

- https://akkogear.jp/pages/downloads
- https://en.akkogear.com/download/
- https://akkogear.jp/pages/software?t=keyboard

## 8.3 ハードウェアリビジョン

公式案内では、TAC75 HEはシリアル番号の下5桁によって使用ドライバーが異なる。

- 32000以下：Cloud Driver V4
- 32001以上：専用Webドライバー

開発時に公式の最新情報および実機情報を確認し、適切なプロトコルを選択すること。

同一製品名でもハードウェアリビジョンによって通信仕様が異なる可能性を考慮する。

## 8.4 Webドライバー解析

Webドライバーが使用可能な場合は、以下を調査する。

1. Webドライバーが要求するHIDデバイス
2. 公開JavaScript
3. WebHID APIの使用有無
4. sendReport
5. sendFeatureReport
6. receiveFeatureReport
7. Report ID
8. 設定値とパケット構造の対応
9. チェックサム
10. 応答処理
11. エラー処理

Webドライバーが利用できない場合は、純正デスクトップドライバーのUSB通信を解析する。

## 8.5 実装対象機能

優先度：最優先

- デバイス検出
- 接続状態取得
- 現在の設定読み込み

優先度：高

- アクチュエーションポイント設定
- ラピッドトリガー設定
- 押下時感度
- 離上時感度
- キーごとの個別設定
- デッドゾーン
- RGBライティング
- プロファイル管理
- 本体への設定保存

優先度：中

- キー割り当て
- ポーリングレート変更

優先度：低

- キー押下深度のリアルタイム可視化
- その他の対応設定

## 8.6 磁気スイッチ設定の注意事項

- 設定可能な範囲を実機または検証済み仕様から取得する。
- 設定値の刻み幅を確認する。
- キーごとの制約を確認する。
- 不正な設定値を送信しない。
- 設定変更前の値を保存する。
- 書き込み後は可能な限り読み戻し確認を行う。

## 8.7 初期開発対象外

- ファームウェア更新
- 磁気スイッチのキャリブレーション
- 工場出荷状態への初期化

これらは通信仕様と復旧方法を十分確認できるまで実装しない。

## 8.8 バッテリー管理

TAC75 HEは有線専用機器として扱う。

- バッテリー監視対象外とする。
- 架空のバッテリー残量を表示しない。
- ダッシュボードにはUSB接続状態を表示する。
- システムトレイの残量アイコンは生成しない。

# 第9章 バッテリー監視機能

## 9.1 基本仕様

バッテリー搭載デバイスの残量および充電状態を継続的に監視する。

初期対応はG PRO X SUPERLIGHTとする。

将来的には複数メーカーのバッテリー搭載デバイスに対応する。

## 9.2 取得情報

- デバイス名
- バッテリー残量
- 充電状態
- 低残量状態
- 接続方式
- オンライン状態
- スリープ状態
- 最終取得時刻

残量を取得できない場合は0%として扱わず、不明状態として管理する。

## 9.3 更新方式

イベント駆動を最優先とする。

HID++等のデバイス通知を利用できる場合は、通知による更新を行う。

基本動作：

- 起動時に残量取得
- 接続時に残量取得
- 再接続時に残量取得
- スリープ復帰時に更新
- 充電開始時に更新
- 充電終了時に更新
- 残量変更通知時に更新
- 手動更新時に再取得

イベント駆動が利用できない場合のみ低頻度ポーリングを行う。

デフォルトのポーリング間隔は60秒とする。

ポーリング間隔はユーザー設定で変更可能とする。

デバイスのスリープを妨げないこと。

## 9.4 状態管理

以下の状態を区別する。

- 正常
- 充電中
- 低残量
- スリープ中
- 切断中
- 残量不明
- 通信エラー

過去の取得値を表示する場合は、最新の実測値ではないことを明示する。

## 9.5 将来的な拡張

- バッテリー残量履歴
- 充電履歴
- 放電速度の記録
- 残り稼働時間の推定

推定値を実測値として表示しないこと。

# 第10章 システムトレイ機能

## 10.1 基本仕様

Windows 11の通知領域にバッテリー残量を表示する。

マウスカーソルを合わせなくても、アイコン内の数値から残量を確認できるようにする。

GUIを開いていない状態でも表示を継続する。

## 10.2 表示モード

### デバイス個別表示

- バッテリー搭載デバイスごとに個別アイコンを生成する。
- アイコン内にバッテリー残量を数字で表示する。
- デバイスの追加・削除に動的対応する。

### 統合表示

- 全監視対象のうち最も低いバッテリー残量を表示する。
- ホバーまたはクリック時に各機器の状態を確認できる。

### バッテリー型表示

- 数字の代わりにバッテリー型アイコンを表示する。
- 残量に応じて充填量を変更する。

初期設定はデバイス個別表示の数値モードとする。

## 10.3 色および表示状態

| 状態 | 表示 |
|---|---|
| 21～100% | 緑色 |
| 11～20% | オレンジ色 |
| 0～10% | 赤色 |
| 充電中 | 青色＋充電マーク |
| スリープ中 | グレー＋最終取得値 |
| 残量不明 | 疑問符 |
| 切断中 | 非表示またはオフライン表示 |

色や閾値は変更可能とする。

充電中は充電状態の表示を優先する。

色だけに依存せず、数値や記号でも状態を確認できるようにする。

## 10.4 アイコン描画

- 16×16相当の小サイズでも数値を判読可能にする。
- 20×20、24×24、32×32相当の表示を考慮する。
- WindowsのDPIスケーリングに対応する。
- ライトテーマ、ダークテーマに対応する。
- 残量に変化がない場合はアイコンを再生成しない。
- GDIリソースリークを防止する。

Windows側の通知領域設定によってアイコンが隠れる場合があるため、必要に応じて常時表示する方法をユーザーに案内する。

## 10.5 ツールチップ

ホバー時に以下を表示する。

- デバイス名
- バッテリー残量
- 充電状態
- 接続方式
- 最終取得時刻
- オンライン／スリープ／切断状態

## 10.6 左クリック

簡易ステータス画面を表示する。

表示内容：

- 接続デバイス一覧
- 各デバイスのバッテリー残量
- 充電状態
- 接続方式
- 最終更新時刻

バッテリー非搭載機器については接続状態のみ表示する。

## 10.7 右クリック

以下のメニューを表示する。

# 第11章 バッテリー通知

## 11.1 通知条件

Windowsの通知機能を利用する。

デフォルト通知条件：

- 20%以下：充電推奨
- 10%以下：バッテリー残量低下
- 5%以下：緊急充電通知
- 100%到達：充電完了

デバイスが正確な残量や充電完了状態を提供できる場合のみ、対応する通知を行う。

## 11.2 通知設定

デバイスごとに以下を変更可能とする。

- 通知の有効／無効
- 通知閾値
- 充電完了通知
- 通知の一時停止

## 11.3 通知制御

- 同一閾値の通知を連続送信しない。
- 充電によって残量が回復した場合は通知状態をリセットする。
- 充電中の低残量通知は原則抑制する。
- 通信エラーを低残量として扱わない。
- Windowsの通知制御を尊重する。

ゲーム中に通知を抑制するオプションを実装する。

ゲームプロセスへのインジェクション、メモリ操作、入力自動化は行わない。

# 第14章 軽量化およびパフォーマンス

## 14.1 目標値

| 測定項目 | 目標 |
|---|---|
| Agent常駐時Working Set | 10MB以下 |
| Agent常駐時Private Bytes | 20MB以下 |
| GUI表示時の合計メモリ使用量 | 100MB以下 |
| アイドル時CPU使用率 | 0.1%以下 |
| 不要な常時描画 | なし |

これらは開発目標であり、実機測定によって評価する。

目標値を満たせない場合は、原因と改善案を報告する。

## 14.2 軽量化方針

- 常駐AgentとGUIを分離する。
- GUI終了時に描画リソースを解放する。
- 不要なWebViewやブラウザエンジンを使用しない。
- イベント駆動を優先する。
- 高頻度ポーリングを避ける。
- 不要なバックグラウンド処理を停止する。
- 状態が変化した場合のみUIやトレイアイコンを更新する。
- Releaseビルドで最適化する。
- 不要な依存ライブラリを追加しない。
- ログ出力による負荷を抑える。

## 14.3 計測項目

- Working Set
- Private Bytes
- CPU使用率
- GPU使用率
- プロセス数
- 起動時間
- GUI表示時間
- ハンドル数
- GDIオブジェクト数
- 実行ファイルサイズ

子プロセスも含めて評価する。

# 第16章 ハードウェア安全性

## 16.1 最重要事項

ハードウェアの破損防止を最優先とする。

通信プロトコルについて、根拠のない推測による実機操作を禁止する。

## 16.2 必須安全対策

- 初期開発は読み取り専用とする。
- 未解析コマンドを実機へ送信しない。
- ランダムなHIDコマンドを送信しない。
- 検証済みコマンドのみ書き込み可能とする。
- VID/PIDを照合する。
- HIDインターフェースを照合する。
- ハードウェアリビジョンを照合する。
- 必要に応じてファームウェアを照合する。
- 設定値の範囲を検証する。
- 書き込み前に取得可能な現行設定を保存する。
- 書き込み後は可能な限り読み戻し検証を行う。
- 失敗時の復旧手順を用意する。
- 無制限のリトライを行わない。
- 純正ソフトとの通信競合を防ぐ。

## 16.3 実機書き込み

対象デバイスの初回書き込み試験を行う場合は、以下をユーザーに説明する。

- 実行する操作
- 使用する通信コマンド
- コマンドの根拠
- 想定される結果
- 発生し得るリスク
- 復旧方法

ユーザー承認後に実施すること。

通常利用時の検証済み設定変更については、都度の開発者承認を必須とはしない。

## 16.4 初期開発で禁止する操作

- ファームウェア更新
- 未確認の初期化コマンド
- 未確認のキャリブレーション
- USBドライバーの無断置き換え
- デバイスのブートローダー操作
- 未確認のオンボードメモリ直接書き込み

## 16.5 ゲーム・アンチチートへの配慮

FiveM等のゲームと併用する可能性を考慮する。

以下を禁止する。

- ゲームプロセスへのインジェクション
- ゲームメモリの読み書き
- ゲーム通信の改変
- 入力自動化
- リコイル制御
- 不正なマクロ機能
- アンチチートの回避
- 独自カーネルドライバーの導入

通常のデバイス設定およびバッテリー監視に限定する。

アンチチートとの完全な互換性を保証できない場合は、その旨を明記する。

# 第18章 ブランチ戦略

## 18.1 基本構成

簡略化したGit Flowを採用する。

| ブランチ | 用途 |
|---|---|
| main | 正式リリース |
| develop | 開発機能の統合 |
| feature/* | 新機能 |
| research/* | 技術・通信調査 |
| fix/* | 開発版のバグ修正 |
| hotfix/* | 正式版の緊急修正 |
| release/* | リリース準備 |
| refactor/* | コード構造改善 |
| docs/* | ドキュメント更新 |

## 18.2 main

- 正式リリース用ブランチとする。
- 常に安定した状態を維持する。
- 直接コミットを禁止する。
- 原則としてreleaseまたはhotfixからのPRのみ受け付ける。
- テスト合格済みのバージョンのみ反映する。

## 18.3 develop

- 開発中の機能を統合する。
- feature、research、fix、refactor、docsの統合先とする。
- 直接コミットを原則禁止する。
- Pull Requestによる統合を必須とする。

## 18.4 feature/*

- 最新のdevelopを基点とする。
- 1ブランチにつき1機能または1Issueとする。
- 無関係な変更を混在させない。
- 機能完成後にdevelop向けのPRを作成する。

## 18.5 research/*

- 通信解析や技術調査に使用する。
- 実験的コードと解析資料を管理する。
- 未検証の実験コードを本番処理へ組み込まない。
- 検証済みの仕様書や安全な成果のみdevelopへ統合する。
- 必要に応じてfeatureブランチへ成果を移植する。

## 18.6 fix/*

- developに存在する不具合を修正する。
- 修正内容を独立したPRとして管理する。

## 18.7 hotfix/*

- mainから作成する。
- 正式版の重大な不具合を修正する。
- 修正後はmainとdevelopの両方へ反映する。

## 18.8 release/*

- developから作成する。
- バージョン番号、CHANGELOG、配布物、最終テストを管理する。
- 原則として新機能を追加しない。
- 完了後はmainに統合する。
- リリース中の修正を必要に応じてdevelopへ反映する。

## 18.9 refactor/*

- コード構造改善
- 保守性改善
- パフォーマンス改善

原則として機能変更と分離する。

## 18.10 docs/*

ドキュメントのみの変更に利用する。

## 18.11 命名規則

原則としてIssue番号を含める。

- feature/Issue番号-機能名
- research/Issue番号-調査対象
- fix/Issue番号-不具合内容
- hotfix/Issue番号-修正内容
- refactor/Issue番号-対象
- docs/Issue番号-対象
- release/vX.Y.Z

例：

- feature/12-logitech-battery
- feature/13-tray-battery
- research/21-akko-tac75-protocol
- fix/32-hid-reconnect
- release/v0.1.0

## 18.12 ブランチ作成時期

将来使用するすべてのブランチを最初から作成しない。

対応するIssueに着手するタイミングで作成する。

統合済みの作業ブランチはユーザー承認または事前に合意された運用ルールに従って削除する。

各Issueを対応するマイルストーンに紐付ける。

# 第21章 Codexの開発ワークフロー

すべての開発タスクにおいて以下を徹底する。

1. リポジトリの状態を確認する。
2. 現在のブランチを確認する。
3. 未コミット変更を確認する。
4. AGENTS.mdを確認する。
5. 関連仕様書を確認する。
6. GitHub Issueを確認または作成する。
7. リモートの最新状態を取得する。
8. 適切なベースブランチを確認する。
9. 作業用ブランチを作成する。
10. 対象機能のみ実装する。
11. テストコードを作成する。
12. 自動テストを実行する。
13. 必要に応じて実機テストを案内する。
14. ドキュメントを更新する。
15. 変更差分を確認する。
16. コミットする。
17. 作業ブランチをPushする。
18. Pull Requestを作成する。
19. CIの結果を確認する。
20. レビュー指摘に対応する。
21. ユーザーへ完了報告する。
22. マージ条件を満たした PR は個別のユーザー承認なしでマージする。

依存するIssueが未完了の場合は、その依存関係を明示し、実装順序を調整する。

GitHubへのアクセス権限がない場合は実施済みと報告せず、必要な接続操作をユーザーに案内する。

# 第22章 コミット規則

Conventional Commitsを採用する。

例：

- feat(logitech): add HID++ battery monitoring
- feat(tray): display battery percentage icon
- feat(akko): add rapid trigger configuration
- fix(hid): handle wireless receiver reconnect
- refactor(agent): separate battery polling service
- perf(tray): reduce unnecessary icon regeneration
- test(logitech): add HID++ response parsing tests
- docs(protocol): document TAC75 HE packet structure
- ci(windows): add release build workflow
- chore(release): prepare v0.1.0

コミットメッセージは原則として英語とする。

- 1コミットには関連性のある変更のみ含める。
- 無関係なコード整理を混在させない。
- 変更内容が追跡可能な粒度とする。
- ユーザーの変更を無断でコミットしない。

# 第23章 Pull Requestおよびマージ

## 23.1 PR基本方針

すべての開発作業は原則としてPull Requestを経由して統合する。

通常の機能開発ではdevelopをマージ先とする。

## 23.2 PR記載項目

### 概要

変更目的と背景。

### 関連Issue

対応するIssue番号。

### 主な変更内容

- 実装機能
- 変更モジュール
- 仕様変更
- 追加依存関係

### 自動テスト結果

- cargo fmt
- cargo clippy
- cargo test
- Windows Release Build

### 実機試験結果

- 使用機種
- VID/PID
- 接続方式
- ファームウェア情報
- 実施操作
- 確認結果
- 未検証項目

実機試験が未実施の場合は明示する。

### パフォーマンス

必要に応じて以下を記載する。

- メモリ使用量の変更前後
- CPU使用率の変更前後
- その他の測定結果

### リスク

- ハードウェア操作
- 通信競合
- 互換性
- 既存機能への影響

## 23.3 PRチェックリスト

- [ ] 仕様書に準拠している
- [ ] 関連Issueが紐付いている
- [ ] 自動テストが合格している
- [ ] 必要な実機試験を実施した
- [ ] 未検証項目を明示した
- [ ] 未確認コマンドを送信していない
- [ ] 無関係な変更を含んでいない
- [ ] ドキュメントを更新した
- [ ] 認証情報や個人情報を含んでいない
- [ ] 既存機能への影響を確認した
- [ ] パフォーマンスへの影響を確認した

## 23.4 マージ方式

feature、fix、refactor、docs等からdevelopへのマージは原則Squash Mergeとする。

releaseおよびhotfixの統合は履歴を追跡できる適切な方式を採用する。

## 23.5 マージ条件

- CIがすべて合格している。
- コンフリクトが解消されている。
- 必要なレビューが完了している。
- ハードウェア操作を伴う場合は必要な実機試験が完了している。
- マージについてはユーザーから包括的な実施許可があるため、個別の承認は不要（2026-11-18改定）。

Codexは上記の品質条件を満たした PR を個別確認なしで main または develop へマージしてよい。

## 23.6 ブランチ保護

GitHubのプランおよび権限で利用可能な範囲において、mainとdevelopにブランチ保護またはRulesetを設定する。

### main

- Pull Request必須
- CI成功必須
- 強制Push禁止
- ブランチ削除禁止
- 直接Push禁止

### develop

- Pull Request必須
- CI成功必須
- 強制Push禁止
- ブランチ削除禁止
- 直接Push禁止

リポジトリ所有者が1人の場合は、GitHubの自己承認制限によりマージ不能にならない方法を採用する。

プラン上、ブランチ保護を使用できない場合は運用ルールによって代替し、その制約を明記する。

# 第24章 GitHub Actions・CI/CD

## 24.1 ci.yml

Pull RequestおよびdevelopへのPush時に実行する。

Windows環境で以下を実行する。

- Rustツールチェーンのセットアップ
- 依存関係のキャッシュ
- cargo fmt --all -- --check
- cargo clippy --workspace --all-targets -- -D warnings
- cargo test --workspace --locked
- cargo build --workspace --release --locked

追加要件：

- Mock Deviceによるテスト
- 通信パケット生成テスト
- 通信パケット解析テスト
- 設定値の境界値テスト
- IPC異常入力テスト
- リソース管理の確認
- 未検証コマンドが通常の本番処理に含まれていないことの確認

CI失敗時はマージしない。

## 24.2 security.yml

- Rust依存関係の脆弱性監査
- cargo audit等による確認
- 依存ライブラリのライセンス確認
- 必要に応じた依存関係更新確認

## 24.3 release.yml

承認済みの正式バージョンタグ作成時に実行する。

- Windows Release Build
- インストーラー作成
- ポータブル版作成
- SHA-256ハッシュ生成
- リリースノート生成
- GitHub Releasesへの成果物登録

公開前に必要な実機検証が完了していることを確認する。

正式タグ作成およびリリース公開はユーザー承認後に実施する。

## 24.4 Actionsの安全性

- 権限を必要最小限とする。
- 通常CIに不要な書き込み権限を付与しない。
- 外部Actionのバージョンを適切に固定する。
- Secretsをログへ出力しない。
- CI成功のみで実機動作保証としない。
- テストを通すためだけに安全性チェックを緩和しない。

- 無断でのファームウェア更新
- 無断でのドライバー変更
- 通信プロトコルの捏造
- 未検証機能を実装済みと報告すること
- 同一実機への無計画な同時通信

## ソフトウェア関連

- 安全性チェックの不適切な緩和
- 不要な依存ライブラリの追加
- 個人情報の無断収集

- ゲームプロセスへのインジェクション
- 入力自動化
- アンチチート回避機能
